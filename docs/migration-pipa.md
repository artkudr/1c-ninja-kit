# Переход с файлового каркаса на сервис задач PiPa

Дата: 2026-11-17. Статус: выполнено (решения приняты 2026-11-17).

## Коротко

Файловый каркас (`taskctl.ps1` + `Задачи/<номер>/Задача.md`, `Состояние.json`,
`Артефакты/<роль>/Круг-NN.md`) заменяется сервисом **PiPa** (PithosPandoras):
локальная база, страница в браузере и MCP. Сервис держит задачи, этапы, отчёты,
статусы и файлы; правила и агенты остаются наши, но переписываются под его
контракт и под более слабые модели: меньше церемоний, меньше файлов, один
словарь вердиктов.

Что уже сделано на этой машине — в разделе «Сделано». Что переписываем и в каком
порядке — в «Работы». Спорные решения — в «Открытые вопросы».

## Сделано

- Сервис установлен в `C:\PithosPandoras`, запускается треем, `/health` отвечает;
  база и ключ лежат рядом с exe.
- Проект `devtools` заведён: корень `C:\1C\projects\devtools`, папка `Задачи`,
  шаблон `{number} - {date}`.
- Роли проекта: Коммандер, Оракул, Колдун, Инквизитор, Бард, Телепат. Часовщик
  убран по решению от 2026-11-17.
- Входы ролей (`config_json.inputs`) настроены: Колдун получает план Оракула
  (необязательный), свой прошлый отчёт и возврат Инквизитора; Инквизитор — план
  (необязательный) и отчёт Колдуна (обязательный); Бард — отчёт и приёмку.
- История перенесена: `pithos-pandoras.exe import` поднял задачи 001 и 002 вместе
  с отчётами (артефакты стали отчётами) и файлами (PNG, JS, PDF). Задачи
  помечены закрытыми вручную.
- Полный круг проверен на тестовой базе: создание → этап → отчёт → возврат
  `на доработку` → новый круг с прошлым отчётом и приёмкой во входах → приёмка →
  закрытие. Сервис и входы работают.
- MCP прописан в глобальном `~/.config/opencode/opencode.jsonc` (сервер `pipa`),
  ключ — в переменной `PIPA_KEY`. Чтобы OpenCode увидел переменную, его нужно
  перезапустить: текущий процесс стартовал до `setx`.

- Импорт не сохраняет статус: все задачи приходят «Новые», виды отчётов
  сводятся к `report`, номера берутся из имени папки. После импорта задачи
  закрываются вручную (`task_set_status`).

## Что меняется по сути

| Файловый каркас | PiPa |
|---|---|
| `new --title --route` | `task_create(project, role, title, statement, route)` |
| `Задача.md` | поле `statement` задачи |
| `Состояние.json`, `Журнал.jsonl` | база сервиса, `task_timeline` |
| `start --role` + скелет артефакта | `stage_start` → `round` + `inputs` |
| `Артефакты/<роль>/Круг-NN.md` | `stage_finish(kind, report)` — markdown в базе |
| `finish --verdict` | `stage_finish(verdict)` |
| доска `Задачи.md`, `board` | веб-доска и `task_list` |
| `block` / `resume` | `task_block` / `task_resume` |
| `validate`, маркеры, лимиты | нет; остаются инварианты сервиса |
| маршрут проверяет скрипт | маршрут держат правила и Коммандер |

Сервис проверяет только механику: одна роль в проекте, один открытый этап на
задачу, один отчёт одного вида на этап, отчёт не редактируется, задачу нельзя
закрыть с открытым этапом. Порядок ролей и качество работы он не проверяет —
это остаётся на правилах.

<details>
<summary>Инварианты сервиса, на которые можно опереться</summary>

- Один открытый этап на задачу: второй `stage_start` даёт `conflict`.
- Отчёт не правится и не удаляется: ошибка — новый отчёт или новый круг.
- Возврат распознаётся по точному слову: `return`, `returned`, `возврат`,
  `на доработку`. «На доработку» и «доработка» — не возврат.
- Виды отчётов: `plan`, `report`, `acceptance`, `guide` (этап);
  плюс `research`, `note` (отчёт к задаче без этапа).
- Папку задачи сервис не создаёт, только подсказывает путь и предупреждает
  `folder_missing`.
- Проекты, роли и статусы заводит человек; через MCP их не создать.

</details>

## Предлагаемая модель

### Роли

Шесть ролей вместо семи. **Часовщик уходит**: его работу — план и критерии
приёмки — делят постановка (критерий готовности пишет Коммандер вместе с
человеком) и Оракул (план). Для слабой модели лишний этап дороже, чем польза:
план, собранный без понимания кода, Колдун всё равно переделывает.

| Роль | Что делает | Отчёт |
|---|---|---|
| Коммандер | заводит задачу, ставит постановку, запускает этапы, закрывает | — |
| Оракул | разбор: как воспроизвести, что менять, риски, план | `plan` |
| Колдун | правка в `src/`, метаданные скиллами, загрузка в ИБ | `report` |
| Инквизитор | поведение на живой базе, дефекты `D1…Dn` | `acceptance` |
| Бард | гайд для человека + PDF | `guide` |
| Телепат | перенос объектов между базами | `report` |

### Маршруты

| Маршрут | Кто | Когда |
|---|---|---|
| `справка` | Оракул | «где в коде», «что за версия» — отчёт `research` без этапа |
| `правка` | Колдун | текст, представление, один метод без проверки поведения |
| `быстрый` | Колдун → Инквизитор | один метод или форма, без транзакций и публичного API |
| `полный` | Оракул → Колдун → Инквизитор | метаданные, форма, СКД, роль, расширение, интеграция |
| `релиз` | Оракул → Колдун → Инквизитор → Бард | то же плюс гайд человеку |
| `синхронизация` | Телепат | перенос объектов между базами |

План Оракула необязателен: на `быстром` его нет, Колдун работает по постановке.
Маршрут — метка задачи и правило, а не механизм: сервис его не исполняет.

### Вердикты

Два слова на все роли:

- `готово` — работа сделана (у Инквизитора — приёмка пройдена);
- `на доработку` — есть дефекты, работа возвращается Колдуну.

Остановка — не вердикт, а `task_block(reason, waiting_for)`; продолжение —
`task_resume`. Так исчезает развилка «сбой / нужен-человек / к-часовщику /
к-оракулу», которую слабая модель путает.

### Постановка вместо файлов

Постановку пишет Коммандер при создании задачи, пять пунктов:

1. где видно (роль, объект, данные);
2. что сейчас и что должно быть;
3. на каких данных проверять;
4. чем считается готово (критерий приёмки);
5. что точно не трогаем.

Критерий из постановки — единственная приёмка. Отдельного файла приёмки нет.

### Отчёты и файлы

- Тексты — только в отчётах сервиса; в папке задачи лежат лишь бинарники и
  черновики, которые нельзя положить в текст: PNG, PDF, выгрузки, `.js`
  сценариев. Отчёт с картинками собирается по `file_add` → `/files/<id>`.
- Папку задачи создаёт та роль, которая кладёт в неё первый файл; у задачи из
  импорта она уже есть. `folder_missing` у задачи без файлов — норма.
- Отчёт каждого круга — новый отчёт. Прошлый не переписывается.

## Что снимаем и что оставляем

Снимаем (это и есть «меньше строгости»):

- скелеты артефактов, маркеры «УДАЛИ ЭТУ СТРОКУ», проверку структуры отчёта;
- отдельные файлы плана и приёмки, обязательные разделы, «Причина возврата»;
- перечень вердиктов на роль, лимит возвратов, «зависание» 40 минут;
- `validate`, доску `Задачи.md`, ручные `board`/`unlock`;
- обязанность роли отдавать конверт в чат.

Оставляем:

- постановку с критерием готовности до начала работы;
- один открытый этап и один круг за раз;
- статику закрывает Колдун, поведение доказывает Инквизитор;
- код и `src/` правит только Колдун; структура — только скиллами контура;
- XML руками не правится, рабочая база не трогается;
- возврат — новый круг, прошлый отчёт не переписывается.

## Риски

- **Маршрут больше не проверяется кодом.** Слабая модель может позвать роли не
  по порядку. Лечится коротким правилом в always-контексте и проверкой
  Коммандера; если начнёт ломаться — вернуть один скрипт-валидатор маршрута.
- **Отчёт живёт только в базе.** Потеря базы — потеря истории; `backup` раз в
  неделю и перед обновлением сервиса. Файлы задач в копию не входят.
- **Импорт истории неполон**: статусы сброшены, виды отчётов сведены к `report`.
  Для чтения истории этого достаточно.
- **Нумерация**: импорт занимает номера из имён папок, новая задача получает
  следующий. Импортировать до создания новых задач.
- **Слабая модель путает `на доработку`** с «На доработку»/«доработкой».
  Слово пишется буквально, регистр важен; проверка — в дымовой задаче.
- **Ключ MCP** лежит в переменной окружения, не в конфиге и не в git. При
  переустановке сервиса ключ пересоздаётся — обновить `PIPA_KEY`.
