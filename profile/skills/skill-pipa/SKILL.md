# Оркестрация в PiPa

PiPa — короткий синоним PithosPandoras, локального сервиса задач. Агент работает с ним только через
MCP: не читает базу, не пишет файлы состояния и не создаёт задачи в обход.
Сервис проверяет проект, роль, обязательные поля и переходы состояний.
**Маршрут он не проверяет** — порядок ролей и качество работы держат правила
агентов и этот скилл.

- Справочник вызовов: `reference.md`.
- Шаблоны настроек и ролей: `templates.md`.
- Источник правды: `docs/Сервис-задач-архитектура.md` в репозитории сервиса
  (на рабочей машине — `C:\PithosPandoras`).

## Перед началом

1. Открой `AGENTS.md` проекта и найди строку:

   ```text
   ## Сервис задач
   Проект: <имя>
   ```

   Строки нет — не угадывай проект по пути и не создавай задачу. Спроси
   человека. Пустой проект — ошибка, а не повод выбрать первый попавшийся.

2. Проверь связь вызовом `project_get`. Если инструментов сервиса нет,
   подключи MCP по шаблону из `templates.md`. Сервис слушает
   `http://127.0.0.1:8787/mcp`, ключ лежит в `pithos-pandoras.key` рядом
   с базой. Ключ не попадает в git и в проектный конфиг.

3. `project_get` показывает роли и статусы. Проекты, роли и статусы заводит
   человек на странице `/projects` и `/p/<проект>/settings`. Через MCP их
   создать нельзя. Неизвестная роль — остановка и просьба зарегистрировать,
   а не выдуманное имя.

## Инварианты

- Один открытый этап на задачу. Повторный `stage_start` той же ролью возвращает
  тот же этап с `resumed: true`; чужая роль получает `conflict`.
- Один отчёт одного вида на этап. Отчёт не редактируется: новый круг — новый
  отчёт.
- Этап открывает Коммандер. Роль начинает с `task_get`: если в `current_stage`
  её роль, она читает входы через `stage_start` (он вернёт открытый этап) или
  `report_get` по `report_id`. Если этап держит другая роль — не работает и
  пишет Коммандеру.
- Номер задачи выдаёт сервис. Папку задачи создаёт сервис; агент берёт
  `folder_path` из ответа и не собирает имя папки из номера.
- Отчёт пишется не одним куском: `report_open` → `report_section` /
  `report_append` → `report_publish` → `stage_finish(report_id=...)`.
  Текста `report` в `stage_finish` больше нет.
- `report_id` — единственное имя идентификатора отчёта. Алиасов `report` и
  `id` нет.
- Нельзя закрыть задачу с открытым этапом.
- `task_next` — только механика: есть этап → `stage_finish`, нет →
  `stage_start`. Какую роль запускать, решает оркестратор.
- След работы — отчёты, файлы и комментарии в задаче. Память агента и чат
  задачу не двигают.

## Как устроен конвейер

Роль — это имя агента, этап — отрезок его работы. Круг — повторный заход той же
роли. Входы роли — данные проекта: от кого, какой вид отчёта, какой круг.

```text
Коммандер создаёт задачу
  → Аналитик      план
  → Исполнитель   отчёт
  → Проверяющий   приёмка
  → Документалист гайд
  → Коммандер закрывает задачу
```

Возврат — не правка старого отчёта, а новый круг:

```text
Проверяющий: report_publish → stage_finish(verdict="на доработку", report_id=...)
  → Исполнитель: новый круг, входы = свой прошлый отчёт + приёмка, которая вернула
  → Проверяющий: новый круг
```

Вердикты `return`, `returned`, `возврат`, `на доработку` сервис считает
возвратом и записывает событие `stage_returned`. Любой другой текст — обычное
завершение. Для успеха держи один словарь, например `принято`.

## Настройка оркестрации в проекте

Если просят «настроить оркестрацию», сначала выясни у человека:

1. Какие роли участвуют и в каком порядке идут.
2. Какой отчёт выпускает каждая роль и какие входы ей нужны.
3. Кто и на каком основании возвращает работу.
4. Что считается завершением задачи.

Дальше сделай пять шагов.

1. **Проект.** Человек создаёт его на `/projects`: корень, папка задач, шаблон
   папки с `{number}`. Две активные записи не должны указывать на одну папку
   задач.
2. **Роли и статусы.** Человек добавляет все роли, включая Коммандера, на
   `/p/<проект>/settings`. Статусы по умолчанию уже есть: новая, в работе,
   ожидание, остановлена, закрыта. Добавляй свои, только если без них не
   обойтись.
3. **Входы ролей.** В `config_json` проекта положи объект `inputs`. Сервис
   читает только его; «маршруты» и лимиты он не исполняет. Пример — в
   `templates.md`.
4. **`AGENTS.md`.** Добавь раздел «Сервис задач» с именем проекта, ролями,
   порядком и правилами возврата. Там же: этап открывает Коммандер, отчёт
   пишется через черновик и публикацию, путь к файлам — из `folder_path`.
   Это единственное место, откуда агент берёт имя проекта.
5. **Инструкции ролей.** Каждой роли дай короткий контракт: что получает,
   что делает, какой отчёт и вердикт отдаёт, когда останавливается. Роль
   начинает с `task_get`, а не с открытия второго этапа. Шаблон — в
   `templates.md`.

После настройки прогони дымовую задачу: создать → один этап → отчёт →
закрыть. Это проверяет связь, роли и входы, но не качество маршрута.

## Цикл Коммандера

1. `task_list` — посмотреть задачи (ответ `{ tasks: [...] }`); `task_get` —
   карточка, отчёты, черновики, файлы, `folder_path`; `stage_get` — статус
   этапа, входы, отчёты и черновики.
2. Новая задача:

   ```text
   task_create(project, role="Коммандер", title, statement, route?, resource?)
   ```

   В ответе `task.number`, `folder_name` и `folder_path`. Папку уже создал
   сервис; агент её не создаёт. `warning: folder_exists` значит, что папка
   была раньше, — не перезаписывай, спроси человека. `route` — просто метка,
   сервис её не исполняет. `resource` — общая метка занятости, например одна
   база 1С.

3. Перед этапом вызови `task_next`. Если этап уже открыт, не открывай
   второй: роль должна закрыть его по `report_id`, иначе разберись, почему
   он висит.
4. `stage_start(project, task, role)` — откроет этап и вернёт `round` и
   `inputs`. Если этап уже открыт этой же ролью, вернётся он же с
   `resumed: true`, это не ошибка. Каждый вход — краткое начало; полный текст
   бери через `report_get` по `report_id`. Пустой `inputs` — либо правил нет,
   либо все они необязательные: проверь `config_json`, а не обходи входы.
5. Роль делает работу. Результат — текст в markdown, а не ссылка на чат.
6. Роль пишет отчёт в черновике: `report_open`, затем `report_section` по
   разделам или `report_append`, проверяет `report_draft`, публикует
   `report_publish` и получает `report_id`.
7. `stage_finish(project, task, role, verdict, report_id, kind?)` — закрывает
   этап по опубликованному отчёту. `kind` по умолчанию берётся из отчёта;
   для плана — `plan`, для приёмки — `acceptance`, для гайда — `guide`.
   Текста `report` в запросе нет.
8. Нужен ещё один отчёт другого вида в том же этапе — `report_put`. Короткая
   заметка по ходу этапа — `stage_note`; комментарий к задаче — `task_note`.
9. Все этапы закрыты и работа принята — `task_close(project, task, role)`.
   Не закрывай задачу «на будущее»: откроют заново через `task_reopen`.

Если работа встала, не крутись в повторах: сначала `stage_note` с состоянием,
затем `task_block` с причиной и, если чего-то ждёшь, с `waiting_for`.
`task_block` закрывает открытый этап; после `task_resume` нужен новый
`stage_start`, а не продолжение старого.

Если ждёшь внешнего события дольше 10 минут, `stage_note` с тем, чего ждёшь и
до какого времени, и закрой этап с тем, что уже проверено. Ожидание — не
работа этапа. Субагент без нового сообщения 30–40 минут — проверить и
перезапустить, а не ждать «само придёт».

## Параллельная работа

- Две независимые работы — две задачи. Один открытый этап на задачу.
- Сбор материалов по одной задаче — без этапов: каждый агент вызывает
  `report_add` со своей ролью, видом `research` и заголовком. Оркестратор
  читает отчёты и закрывает задачу.
- Два параллельных этапа в одной задаче не поддерживаются. Не пытайся обойти
  это двумя `stage_start`.
- Общий ресурс (база, стенд) помечай одинаковым `resource` при создании
  задач. Сервис предупредит, но не запретит.

## Дисциплина работы

Эти правила не проверяет сервис. Их держат промпты ролей и Коммандер.

- **Этап.** Открывает Коммандер. Роль начинает с `task_get`, а не с попытки
  открыть второй этап. `stage_start` безопасен: та же роль получит `resumed`.
- **Отчёт.** Пишется разделами по мере готовности, а не одним куском в конце.
  Незакрытые пункты перечисляются явно, а не замалчиваются.
- **Файлы.** Путь берётся из `folder_path` или передаётся `file_name`. Имя
  папки из номера не собирается.
- **Поиск.** Сначала индекс проекта и метаданные; `grep` — по конкретному
  файлу, если индекс не отвечает. В отчёте одна строка, почему `grep`.
- **Приёмка.** Один сценарий — один файл в папке задачи (`Проверки`).
  Повторный круг переиспользует файл, а не пишет сценарий заново inline.
- **Тестовые учётки.** Потребность выясняется на этапе плана. Создание и
  уборка — отдельный шаг, а не импровизация посреди приёмки. Нет учётки —
  приёмка по этому пункту не начинается, Коммандер ставит задачу в ожидание.
- **Ожидание.** Дольше 10 минут — `stage_note` с тем, чего ждёшь, и закрытие
  этапа с тем, что уже проверено.
- **Субагент.** Нет нового сообщения 30–40 минут — проверить и перезапустить.

## Отчёты и файлы

- Отчёт этапа пишется в черновике: `report_open`, `report_section`,
  `report_append`, `report_draft`, `report_publish`. Публикация создаёт
  неизменяемый отчёт и возвращает `report_id`.
- `stage_finish` закрывает этап по `report_id`; `report_put` — дополнительные
  виды (`report`, `plan`, `acceptance`, `guide`).
- `report_add` пишет отчёт прямо к задаче (`report`, `plan`, `acceptance`,
  `guide`, `research`, `note`), без этапа.
- Черновик не попадает во входы роли и в `reports[]`; он виден в карточке
  отдельно. Чужой черновик можно читать, но не писать.
- `report_get` принимает только `report_id`.
- Файл добавляется через `file_add`: `path` от корня проекта или `file_name`
  внутри папки задачи. Путь из ответа `folder_path` — основной ориентир.
  Потом ссылка `/files/<id>` вставляется в текст отчёта.
- Отчёт не редактируется и не удаляется. Ошибка в отчёте исправляется новым
  кругом или новым отчётом.

## Ошибки

Ошибка приходит как `{code, message, hint, allowed}`. Не перебирай варианты
наугад.

| Код | Что делать |
|---|---|
| `project_missing`, `project_unknown` | взять имя из `AGENTS.md`; список — в `allowed` |
| `role_missing`, `role_unknown` | остановиться и попросить зарегистрировать роль |
| `task_missing`, `task_unknown` | уточнить номер или идентификатор задачи |
| `field_missing` | заполнить поле; `allowed` показывает допустимые значения |
| `field_invalid` | значение есть, но неверное или пустое; прочитай `hint` |
| `input_missing` | нет обязательного входа: проверить круг, вид и `config_json` |
| `conflict` | этап занят другой ролью, дубль вида или черновик уже опубликован |
| `not_found` | нет отчёта, черновика, файла или события: проверить идентификатор |
| `file_not_found` | файла нет; в `path` — как передали, в `tried` — что искали |
| `io` | проблема диска или базы: остановиться и показать человеку |

## Чего не делать

- Не подставлять «последнюю задачу» и не создавать роли или проекты на лету.
- Не обходить `stage_start` и не писать отчёт в обход черновика,
  `report_publish` или `report_put`.
- Не передавать в `stage_finish` текст `report`: только `report_id`.
- Не собирать имя папки задачи из номера: брать `folder_path` или `file_name`.
- Не закрывать задачу, пока есть открытый этап или непринятая работа.
- Не хранить секреты и ключ MCP в проектном конфиге или в git.
- Не считать, что сервис проверит порядок ролей: это работа оркестратора.
