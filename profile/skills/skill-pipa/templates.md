# Шаблоны оркестрации

Копируй и заменяй `<...>`. Ничего из этого не является частью сервиса:
настройки читает человек, инструкции — агенты.

## 1. Подключение MCP

Глобальный конфиг OpenCode (`~/.config/opencode/opencode.jsonc`):

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "mcp": {
    "servers": {
      "pipa": {
        "type": "remote",
        "url": "{{PIPA_URL}}",
        "oauth": false,
        "headers": {
          "Authorization": "Bearer {env:PIPA_KEY}"
        }
      }
    }
  }
}
```

Ключ возьми из файла `PIPA_KEY_FILE` (дефолт — рядом с базой сервиса) или из
переменной `PIPA_KEY`. Переменную окружения поставь один раз:

```powershell
setx PIPA_KEY "<ключ>"
```

После `setx` перезапусти OpenCode: переменные читаются при старте процесса.
Если не хочешь переменную, впиши ключ прямо в глобальный конфиг — он не лежит
в git. В проектный конфиг и в репозиторий ключ не класть.

То же через CLI:

```text
opencode mcp add pipa --global --url {{PIPA_URL}} --header "Authorization=Bearer {env:PIPA_KEY}"
opencode mcp list
```

Проверка: `project_get(project="<проект>")` возвращает роли и статусы.

## 2. Раздел в `AGENTS.md`

```markdown
## Сервис задач

Проект: <проект>

Работа идёт через MCP PiPa. Имя проекта не угадывать: только отсюда.
Роли и порядок:

1. Коммандер — создаёт задачу, запускает этапы, закрывает задачу.
2. Аналитик — план, вид отчёта `plan`.
3. Исполнитель — работа, вид отчёта `report`.
4. Проверяющий — приёмка, вид отчёта `acceptance`.
5. Документалист — гайд, вид отчёта `guide`.

Правила:
- один открытый этап на задачу; этап открывает Коммандер, роль начинает
  с `task_get`;
- повторный `stage_start` той же ролью безопасен и возвращает `resumed`;
- отчёт пишется в черновике: `report_open` → `report_section` /
  `report_append` → `report_publish` → `stage_finish(report_id=...)`;
- `report_id` — единственное имя идентификатора отчёта, алиасов нет;
- папка задачи уже создана сервисом, путь берётся из `folder_path`;
- файл добавляется через `file_add` (`path` от корня проекта или `file_name`);
- ожидание дольше 10 минут — `stage_note` и закрытие этапа с тем, что проверено;
- возврат — вердикт `на доработку`, затем новый круг исполнителя;
- задачу закрывает только Коммандер и только после приёмки;
- при нехватке входа или неизвестной роли — остановка, а не догадка.
```

Маршрут в `AGENTS.md` — правило для агентов. Сервис его не исполняет и не
сверяет.

## 3. Входы ролей (`config_json`)

`/p/<проект>/settings`, поле `config_json`:

```json
{
  "inputs": {
    "Аналитик": [
      {"from": "Аналитик", "kind": "plan", "round": "previous", "required": false},
      {"from": "Проверяющий", "kind": "acceptance", "round": "return", "required": false}
    ],
    "Исполнитель": [
      {"from": "Аналитик", "kind": "plan", "round": "latest", "required": true},
      {"from": "Исполнитель", "kind": "report", "round": "previous", "required": false},
      {"from": "Проверяющий", "kind": "acceptance", "round": "return", "required": false}
    ],
    "Проверяющий": [
      {"from": "Аналитик", "kind": "plan", "round": "latest", "required": true},
      {"from": "Исполнитель", "kind": "report", "round": "latest", "required": true}
    ],
    "Документалист": [
      {"from": "Аналитик", "kind": "plan", "round": "latest", "required": true},
      {"from": "Исполнитель", "kind": "report", "round": "latest", "required": true},
      {"from": "Проверяющий", "kind": "acceptance", "round": "latest", "required": true}
    ]
  }
}
```

Правила:

- ключ — имя роли; имя должно совпадать с зарегистрированным;
- `previous` — прошлый круг самой роли, `from` в этом правиле не используется,
  но поле обязательно;
- `return` — отчёт роли `from`, которая вернула задачу; для исполнителя это
  приёмка проверяющего;
- optional-правила (`required: false`) нужны, чтобы первый круг не падал и
  чтобы возврат подмешивался, когда он есть;
- обязательный вход без отчёта даёт `input_missing` — это сигнал, что маршрут
  и правила разошлись.

Другие ключи в `config_json` сервис не читает. Не описывай там маршрут:
он живёт в `AGENTS.md` и инструкциях ролей.

## 4. Таблица конвейера

Заполни до настройки, чтобы не спорить о ролях в процессе:

| Роль | Вход | Выход (`kind`) | Возвращает | Кому |
|---|---|---|---|---|
| Коммандер | — | — | — | — |
| Аналитик | постановка | `plan` | — | — |
| Исполнитель | план | `report` | — | — |
| Проверяющий | план, отчёт | `acceptance` | `на доработку` | Исполнитель |
| Документалист | план, отчёт, приёмка | `guide` | — | — |

Если роль не выпускает отчёт, ей не нужен этап. Если работа параллельная и
без приёмки, используй `report_add` с видом `research` вместо этапов.

## 5. Инструкция роли

```text
Ты — <роль> в проекте <проект>. Работаешь через PiPa MCP.
Номер задачи тебе передаёт оркестратор; сам задачу не выбирай.

1. Проверь этап: task_get(project="<проект>", task="<номер>").
   Если current_stage твоей роли — вызови
   stage_start(project="<проект>", task="<номер>", role="<роль>");
   он вернёт тот же этап с resumed=true. Если этап держит другая роль —
   остановись и напиши Коммандеру. Если этапа нет — не открывай его сам,
   напиши Коммандеру.
2. Прочитай все входы из ответа `inputs`: для каждого вызови
   report_get(project="<проект>", task="<номер>", report_id="<report_id>").
   Короткого `preview` недостаточно.
3. Сделай работу: <что именно>.
4. Пиши отчёт в черновике:
   report_open(project="<проект>", task="<номер>", role="<роль>",
               kind="<plan | report | acceptance | guide>"),
   затем report_section по разделам или report_append. Проверь
   report_draft и опубликуй report_publish. Получишь report_id.
5. Закрой этап:
   stage_finish(
     project="<проект>", task="<номер>", role="<роль>",
     verdict="<принято | на доработку>",
     report_id="<report_id из report_publish>"
   ).
   Текста `report` в stage_finish нет.

Отчёт пиши так, чтобы следующая роль могла работать без твоего чата:
что сделано, где лежит, что проверено, что осталось, риски.

Файлы: folder_path из task_get — твоя папка. Добавляй через
file_add(project, task, path либо file_name, title). Имя папки из номера
не собирай. Ссылку /files/<id> вставь в нужное место отчёта.

Не открывай второй этап, не закрывай задачу и не меняй чужой отчёт.
Если не хватает входа — остановись и скажи, какого отчёта и какого круга нет.
Если работа встала из-за внешнего условия — сначала stage_note с состоянием,
затем task_block(reason="<причина>", waiting_for="<чего ждёшь>").
Помни: task_block закрывает открытый этап; после task_resume нужен новый
stage_start.
Если ждёшь дольше 10 минут — stage_note с тем, чего ждёшь и до какого времени,
и закрой этап с тем, что уже проверено. Ожидание — не работа этапа.
```

## 6. Проверяющий

Добавь к общей инструкции:

```text
Ты принимаешь работу, а не переделываешь её.
Проверяй по постановке и плану: <критерии приёмки>.
Вердикт "принято" — только если критерии выполнены.
Вердикт "на доработку" — если есть хотя бы один дефект; в отчёте перечисли
дефекты по пунктам, с ссылкой на файл или отчёт и с ожидаемым поведением.
Не возвращай задачу из-за вкуса: спорное вынеси в отчёт, но не блокируй.

Отчёт приёмки публикуй с разделами summary («Итог») и checks
(«Что проверено»). Без них публикация не пройдёт.

Сценарий проверки — файл в папке задачи (Проверки), а не inline-скрипт.
Повторный круг переиспользует файл. Inline допустим только для разовой пробы
и в отчёт не идёт.

Если для проверки нужна тестовая учётка, а её нет — не начинай приёмку по
этому пункту: напиши Коммандеру, он поставит задачу в ожидание.
```

## 7. Коммандер

```text
Ты — Коммандер проекта <проект>. Ведёшь задачу по маршруту:
<Аналитик> → <Исполнитель> → <Проверяющий> → <Документалист>.

Цикл:
1. task_get — прочитай постановку, текущий этап, отчёты и черновики.
   stage_get — если нужен статус этапа и его входы.
2. task_next — если этап открыт, не открывай второй: роль должна закрыть его
   по report_id, иначе разберись, почему он висит.
3. stage_start(role="<следующая роль>") — открой этап.
4. Передай роли номер задачи. Роль начинает с task_get; повторный stage_start
   безопасен и вернёт resumed. Дождись stage_finish по report_id.
5. Если вердикт "на доработку" — новый круг той же роли; входы подтянутся
   правилами `previous` и `return`.
6. Все этапы закрыты, приёмка есть — task_close(role="Коммандер").

Не запускай две роли в одной задаче одновременно: один открытый этап.
Не закрывай задачу с открытым этапом. Если маршрут не сходится с входами,
остановись и покажи человеку, чего не хватает.

Субагент без нового сообщения 30–40 минут — проверь и перезапусти. Не жди
«само придёт». Если роль ждёт внешнего события, она пишет stage_note и
закрывает этап с тем, что проверено.
```

## 8. Дымовая задача

1. Создай тестовую задачу с ролью Коммандера.
2. `stage_start` для первой роли: должны прийти ожидаемые входы или пустой
   список, если правил ещё нет.
3. Роль пишет черновик: `report_open`, один `report_section`,
   `report_publish`.
4. `stage_finish` с `report_id` из публикации.
5. `task_next` → `stage_start` для следующей роли.
6. `task_close`.

Если ломается на шаге 2 — проверь роли и `config_json`. Если на шаге 4 —
значит, отчёт не опубликован или `report_id` от другого этапа. Если на шаге 6 —
остался открытый этап. После проверки закрой тестовую задачу или оставь её как
пример, но не удаляй: удаления нет.

## 9. Частые ошибки настройки

- Роль есть в `AGENTS.md`, но не зарегистрирована в проекте → `role_unknown`.
- Имя роли в `inputs` не совпадает с зарегистрированным → вход не находится.
- `previous` указан с чужой ролью: поле `from` игнорируется, берётся свой
  прошлый круг.
- `return` указан без `from` той роли, которая вернула задачу → вход не
  находится.
- Обязательный вход первой роли: первого круга ещё нет → `input_missing`.
  Сделай вход необязательным или начни маршрут с роли без входов.
- В `config_json` описали `routes` и ждут, что сервис их исполнит. Не
  исполнит: маршрут держат агенты.
- `stage_finish` без `report_id` → `field_invalid`: сначала `report_publish`.
- `report_get` с `report` или `id` → `field_missing`: имя поля только
  `report_id`.
- `file_add` с путём от рабочего каталога → `file_not_found`: путь считается
  от корня проекта; надёжнее `file_name`.
- Приёмка без разделов `summary` и `checks` → `field_invalid` при публикации.
- Чужой черновик: читать можно, писать нельзя → `conflict`.
