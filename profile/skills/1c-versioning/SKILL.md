# Версионирование 1С: CFE, EPF, ERF

**Правило обязательное.** Каждая доработка расширения, внешней обработки или отчёта сопровождается повышением версии. Версия — строка из **4 блоков чисел**, разделённых точками: `X.Y.Z.W`.

## Схема: что увеличиваем

| Блок | Счёт | Название | Когда увеличиваем | Пример |
|------|------|----------|-------------------|--------|
| **X** | 1-е / 4-е с конца | Релиз | Функционал стабилен, **формат данных определён** → выпускаем релиз | `0.9.4.2` → `1.0.0.0` |
| **Y** | 2-е / 3-е с конца | Новый самостоятельный функционал | В **этом** объекте появляется сценарий, которого раньше не было | `0.1.0.0` → `0.2.0.0` |
| **Z** | 3-е / 2-е с конца | Развитие существующего | Добавляем шаг или опцию **внутрь уже работающего** сценария | `0.3.0.0` → `0.3.1.0` |
| **W** | 4-е / 1-е с конца | Мелкая доработка | Исправления, опечатки, правки **без новой возможности** для пользователя | `0.3.1.0` → `0.3.1.1` |

## Как выбрать разряд

Вопрос один: **этой пользовательской возможности в данном расширении/обработке ещё не было?**

1. **Не было** → **Y**. Новый сценарий, новый вид работы, перенос целого функционала из другого расширения, новый тумблер + логика под отдельную задачу. Объём кода, число перехватчиков и то, что объект уже «большой хаб», **не важны**.
2. **Уже была, добавляем кусок внутрь** → **Z**. Обработка артикула внутри уже существующей загрузки из Excel; подбор по наименованию в уже существующем подборе; ещё один документ в уже существующей печати чека.
3. **Возможность та же, меняется только корректность/текст** → **W**.
4. **Релиз текущего состава** (всё работает, формат данных определён) → **X** = `1` (или следующее число релиза). Это условие среза релиза, а не запрет дальше поднимать Y.

**Типичная ошибка:** «в расширении уже есть другой функционал, значит новый сценарий — небольшой блок (Z)». Нет. НДС в чеке, которого в расширении не было — это **Y**, даже если рядом уже живут другие доработки. Z — только развитие *того же* сценария.

После релиза (`X ≥ 1`) правило то же: новый самостоятельный функционал — `1.0.0.0` → `1.1.0.0`, а не `1.0.1.0`.

## Правила повышения

1. **Начальная версия** нового пустого расширения/обработки — `0.1.0.0`. Затем повышается при добавлении функционала.
2. **Старшие слева не трогаем, младшие справа сбрасываем в 0:**
   - новый функционал: `0.3.2.1` → `0.4.0.0`;
   - развитие сценария: `0.3.2.1` → `0.3.3.0`;
   - мелкая правка: `0.3.2.1` → `0.3.2.2`;
   - релиз: `0.9.4.2` → `1.0.0.0`.
3. **Пропуск блоков недопустим** (не перескакиваем с `0.2.0.0` на `0.5.0.0`).
4. **`0.0.0.0` — запрещена** (недопустимое значение).
5. **До релиза (X = 0)** всё, что попадает в базу и используется, — это серия `0.Y.Z.W`.
6. **Первое число (X)** становится `1`, когда *текущий* состав работает и **формат данных определён**. Последующие новые сценарии по-прежнему поднимают Y.
7. Версия не «сбрасывается вниз»: если в базе у объекта уже есть версия, новая должна быть **больше** неё (лексикографически).

## Где хранится версия

| Объект | Файл | Тег |
|--------|------|-----|
| Конфигурация | `src/cf/Configuration.xml` | `<Version>` |
| Расширение (CFE) | `src/cfe/<Имя>/Configuration.xml` | `<Version>` |
| Внешняя обработка (EPF) | `src/epf/<Имя>/<Имя>.xml` | `<Version>` (если есть) |
| Внешний отчёт (ERF) | `src/erf/<Имя>/<Имя>.xml` | `<Version>` (если есть) |
| EPF/ERF, подключённые через БСП | `src/epf/<Имя>/<Имя>/Ext/ObjectModule.bsl` (или `src/erf/…`) — функция `СведенияОВнешнейОбработке` | `ПараметрыРегистрации.Версия` |

Для EPF/ERF, подключаемых через подсистему БСП «Дополнительные отчёты и обработки», версия, которую видит пользователь в реестре дополнительных обработок, задаётся в `ПараметрыРегистрации.Версия` внутри функции `СведенияОВнешнейОбработке`. При изменении версии обработки обновляй её здесь.

**Не путать** с `ConfigurationExtensionCompatibilityMode` (режим совместимости платформы) — он не меняется при версионировании.

## Процесс

1. Ответь на вопрос «этой возможности в объекте ещё не было?» и выбери Y / Z / W / X.
2. Найди текущую версию в `src/` (см. таблицу).
3. Обнови версию в соответствующих местах:
   - CFE/конфигурация: `<Version>` в `Configuration.xml` (предпочтительно через скилл `meta-edit`);
   - EPF/ERF: `ПараметрыРегистрации.Версия` в `СведенияОВнешнейОбработке` (через скилл `epf-bsp-init` / `epf-bsp-add-command`), при наличии `<Version>` в корневом XML — и его.
4. Сопроводи изменения summary: «версия N → N+1, что изменилось, какой разряд и почему».
5. Валидируй изменения (скиллы `*-validate`) и при загрузке в ИБ передай новую версию.

## Примеры

| Действие | Разряд | Было | Стало |
|----------|--------|------|-------|
| Создали пустое расширение | — | — | `0.1.0.0` |
| Добавили загрузку из Excel (сценария не было) | Y | `0.1.0.0` | `0.2.0.0` |
| Добавили подбор значений из базы по файлу (новый сценарий) | Y | `0.2.0.0` | `0.3.0.0` |
| Внутри загрузки Excel сделали обработку артикула | Z | `0.3.0.0` | `0.3.1.0` |
| В том же подборе добавили поиск по наименованию | Z | `0.3.1.0` | `0.3.2.0` |
| Исправили формирование текста сообщения | W | `0.3.2.0` | `0.3.2.1` |
| Добавили НДС в чеке — этого сценария в расширении не было | Y | `0.3.2.1` | `0.4.0.0` |
| Перенесли в расширение целый готовый функционал (кредитный лимит и т.п.) | Y | `0.4.0.0` | `0.5.0.0` |
| В уже существующем НДС в чеке поддержали ещё один документ оплаты | Z | `0.5.0.0` | `0.5.1.0` |
| Релиз: текущий состав работает, формат данных определён | X | `0.9.4.2` | `1.0.0.0` |
| После релиза добавили новый самостоятельный сценарий | Y | `1.0.0.0` | `1.1.0.0` |

## Связанные скиллы

- `meta-edit` — правка `<Version>` в `Configuration.xml`.
- `cfe-init`, `epf-init`, `erf-init` — создание объектов (в параметрах `Version` задают начальную `0.1.0.0`).
- `repo-workflow` — для CFE из `repository.json` после смены версии: lock → XML → load → commit (гейты из скилла).
