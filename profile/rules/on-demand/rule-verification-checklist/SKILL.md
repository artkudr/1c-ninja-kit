# Verification checklist

Грузи перед объявлением non-trivial изменения «готово». Компаньоны: `rule-tooling-playbooks`, `rule-systematic-debugging`, `rule-development-process`.

Проверки делятся по владельцу: статику закрывает Колдун до сдачи, поведение доказывает Инквизитор на живой базе. Один и тот же прогон дважды не делается: повтор линтера ничего не доказывает, а второй владелец только тратит бюджет.

## Статика — Колдун, до сдачи

### 1. Analyzer — `diagnostics file`

На каждый затронутый `.bsl`. Pass: нет `error`. Бюджет: 1 вызов на цикл правки; до 3 только после substantive дефекта. Без no-change повторов. Вывод — в артефакт Колдуна.

### 2. Напарник `check_1c_code` (если MCP доступен)

После gate 1. Pass: нет critical/error. Если сервер не поднят — **не блокируй**: зафиксируй в Risks «Напарник недоступен» и опирайся на diagnostics.

### 3. Напарник `review_1c_code` (если доступен)

Стиль / ITS. Та же деградация, что gate 2. Дополнительно: `v8std_explain_*` при разборе находки.

### 4. Impact (`graph`)

Обязателен, если менялась публичная поверхность / метаданные / экспорт. `resolve` → `callers` / `neighbors`. Если graph недоступен — явная строка в Risks, не молчаливый skip.

### 5. Metadata / form validation

Если трогали XML структуры: профильный `*-validate` (meta/form/skd/…). Для CFE с хранилищем — гейты `skill-repo-workflow`. Для EPF/ERF — `epf-validate` / `erf-validate` и сборка.

### 6. Platform / load gates

По скиллам контура: `live_check_syntax` и `live_validate_query` для новых фрагментов и запросов; `db-cfe-admin check` для расширений; load только скиллами контура (`db-load-xml` / `skill-repo-workflow`).

«Собралось» и «загрузилось» — два разных гейта. Неудачный load из-за занятой базы, чужого сеанса или незавершённого обновления — среда: причина в Risks, повтор по плейбуку, бюджет правок не расходуется.

Разрешение на загрузку в тестовую базу спрашивается один раз при создании задачи и записывается в постановку. Дальше load идёт без подтверждения, а summary — в отчёт круга. Повторно спрашивать только при смене целевой базы.

## Поведение — Инквизитор, на живой базе

| Что менялось | Чем доказывается |
| --- | --- |
| Серверная логика, движения | `live_query` по данным после сценария, `live_event_log` |
| Форма, команда, отчёт, интерфейс | `skill-web-test` — сценарий шагами, экран до и после |
| Визуальный вид, печать, вёрстка | эталон и числовой допуск: DOM-геометрия или сравнение PNG; один эталон на задачу |
| Повторяемый признак, регресс | `skill-web-test test` — набор в реестре проекта `tests/web-test/`, прогон и отчёт |
| Права и роли | сценарий под пользователем с нужной ролью |
| Обмен и перенос | контрольные значения до и после |

Инквизитор не повторяет линтеры и `*-validate`: он берёт из артефакта Колдуна только список изменённого. Нет вывода статики в артефакте — не дефект приёмки; битая сборка видна как отказ объекта в базе.

## Печатная форма — `rule-print-forms`

- Растр — только логотип, слоган, оттиск, факсимиле, подпись, QR. Шапка, шапка таблицы, полосы, линии, рамки и весь текст — ячейки.
- `ТабличныйДокумент.Рисунков` равно числу настоящих растров; больше — в макет попал кусок образца.
- В PDF текст шапки, шапки таблицы и нижней полосы извлекается как текст; картинки не перекрывают текст.
- Геометрия и цвета — в допуске приёмки; эталон один на задачу.

## Soft gates

| Когда | Что |
|--------|-----|
| Debug | Reproduction case закрыт (`rule-systematic-debugging`) |
| Full-cycle с планом | План выполнен; нет файлов вне плана (`git diff --name-only`) |
| UI | `skill-web-test` — если менялся интерфейс, обязателен, а не «по просьбе» |
| Code review | Только если пользователь просил |

## Delivery summary (обязательно)

- Что изменено и почему (пути в backticks)
- Какие гейты пройдены / пропущены и почему, с указанием владельца (статика / поведение)
- Risks / follow-ups

Объявлять «готово» при провале hard gate запрещено.
