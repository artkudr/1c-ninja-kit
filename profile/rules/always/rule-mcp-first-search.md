# Поиск по исходникам 1С: сначала индекс

Любой поиск по исходникам 1С — BSL, метаданные, формы, запросы, usages — начинается с индекса проекта.
`grep` / `glob` — запасной путь, а не первый.

## Порядок

1. `bsl-analyzer-workspace` `search` → `action: "search_code"`, `query` — по смыслу и по имени.
2. Нужен XML выгрузки → `1c-ninja-mcp` `xml_search` (`path` — корень выгрузки, напр. `src/cf`).
   Нужна структура объекта → `bsl-analyzer-workspace` `metadata` (`action: "object"`).
   Нужен граф вызовов → `graph` (`resolve` → `callers`).
3. Только потом `grep` / `glob` — и с одной строкой-причиной: что уже пробовал и почему MCP не хватил.

## Почему не наоборот

Типовая выгрузка ERP — десятки тысяч файлов и единицы гигабайт. Поиск через PowerShell
(`Select-String`, `Get-ChildItem | Select-String`) по такой конфигурации идёт минутами,
индекс отвечает за доли секунды. Тот же запрос, тот же ответ, разница на порядки.

## Ограничения

- `grep` по исходникам — всегда с `path` (`src/cf`) и `include` (`*.bsl`, `*.xml`).
  Поиск по всему воркспейсу задевает `vendor/` и кеш `.build/` — это пустая работа.
  В проектах кита есть `.ignore` — `rg` уже исключает `build/`, `.build/`, `vendor/`; руками исключать не нужно.
- Поиск по коду через shell (`Select-String`, `findstr`, `Get-ChildItem | Select-String`) — не использовать.
  `rg` в PATH — можно.
- Без MCP-попытки `grep` / `glob` — только по тому, что MCP не индексирует: `.md`, rules, `handoffs/`,
  логи, `openspec/`, JSON/YAML-конфиги, `.v8-project.json`, `bsl-analyzer.toml`.

## Если индекс не готов

- `status: "not_ready"`, `loading`, retry-envelope — это не «ничего не нашлось». Подожди и повтори.
- Холодная сборка индекса на большой конфигурации — минуты. Это повод подождать, а не переключиться на grep.
- Сервер не поднят (инструмента нет в каталоге, `connection closed`) — инфраструктурная поломка:
  скажи пользователю. `grep` — временный обход, и называй его явно.

Маршруты по видам задач и частые ошибки — скилл `skill-bsl-analyzer`.
